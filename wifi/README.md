# Built-in Wi-Fi (BCM43602) on the MacBookPro13,2

The only FullMAC firmware brcmfmac has for this chip (linux-firmware
`brcmfmac43602-pcie.bin` 7.35.177.61, 2015) does not understand Apple's SROM
(signature 0x9999), so without a board NVRAM it runs on the reference board
data: dummy MAC, no 5 GHz, RX 33-39 dB too weak, connects time out (status 16).

`sudo mbp-wifi nvram` reads the chip's own external SROM through ChipCommon
(read-only: only the READ opcode is ever issued, see `read_srom.py`), checks it
(Apple signature, rev 12, CRC8, 14e4:43ba / 106b), decodes it with Broadcom's
SROM tables (`srom_tables.py`, generated by `gen_srom_table.py` from bcmdhd
`bcmsrom_tbl.h`) and writes
`/lib/firmware/brcm/brcmfmac43602-pcie.Apple Inc.-MacBookPro13,2.txt` as
`w1.recipe` says, then reloads brcmfmac. The SROM copy goes to
`/var/lib/mbp-wifi/srom.bin` (0600). Neither file belongs in git or in a bug
report: they hold the MAC address and calibration data of your board.
`sudo mbp-wifi remove` deletes the NVRAM again (back to stock).

    sudo ./install.sh wifi     # tools + sleep hook   (wifi-remove: all of it, NVRAM too)
    sudo mbp-wifi nvram

MacBookPro13,2 only: the fixed values below were tuned there.

## Why the fixed values in w1.recipe (all tested 2026-10-15/16)

- `boardflags3=2`: bit 0x08000000 (FORCE_EXT_LPO) hangs the firmware; the low
  bits (FEMCTRL_SUB) select the FEM control table.
- `femctrl=2` + sub 2: with the SROM's femctrl 2 sub 5 the transmitter stays
  silent. femctrl 3 sub 0 (the firmware's table matching Apple's `mch5`) works
  on 2.4 GHz but 5 GHz downloads stall at ~0.1 MB/s (long frames are lost and
  the AP falls back to 6 Mbit/s; VHT, A-MSDU and BT coex ruled out). femctrl 2
  sub 2: 5 GHz 12-29 MB/s down.
- `boardflags=0x00400001`: external-LNA bits 0x1000 / 0x10000000 cleared,
  RX better by ~10 dB.
- `sromrev=11`, `pa2ga*`/`pa5ga*`, `rxgains*`, `pcieingress_war`, `antswitch`,
  `seci_on_sprom`, `txchain`/`rxchain`, `mcsbw160*`: rev-11 layout that the
  2015 firmware parses, values from the firmware's own embedded NVRAM. The
  rev-12-only `rssi_*`, `rxgaintempcoeff*` and `*_txcal` hang it and are left out.
- `maxp*=60`: TX capped at 15 dBm (the SROM allows 20 dBm on 2.4 GHz and
  18 dBm on 5 GHz). Do not use `iw ... txpower`: brcmfmac sets an override.

Result: 2.4 GHz -43..-55 dBm, 5 GHz -30..-38 dBm (macOS -42 / -32); WPA2-PSK
and WPA2-Enterprise (PEAP) work; 5 GHz 12-29 MB/s down / 5-6 MB/s up.
`etc/modprobe.d/brcmfmac.conf` (`install.sh base`): `feature_disable=0x82000`
(firmware supplicant off, the wpa_supplicant 2.11 regression) and
`roamoff=1` (the firmware's own roaming broke connections). NetworkManager
with the iwd backend was used.

## Sleep on the charger (`mbp-wifi.sleep`)

On the charger, with the lid closed, the Mac woke a few seconds into a sleep,
through no GPE the OS sees; in airplane mode it slept. The Broadcom firmware
stays alive in D3 while the charger powers the slot. The hook unloads
`brcmfmac` before a sleep (its remove resets the chip) and loads it after,
only when Wi-Fi is on: airplane mode stays, Bluetooth is not touched. 7 of 7
sleeps on the charger clean, reconnect ~4 s; not connected after 25 s -> one
`nmcli device connect`. Journal tag `mbp-wifi-sleep`.
